# Agentic Development Workflow

## Van esélyünk az AI-jal szemben?

* Ha okosabb nálunk, akkor úgyis mindegy
* Ha nem, akkor meg ne mi menjünk utána

Gyorsabban ír kódot, mint te valaha. De hogyan tudod vállalni érte a felelősséget, ha nem tudod, hogy mi a mögöttes gondolat.

Vibe coding csak olyan helyeken működik, ahol nem fontos a konzisztens működés. (`utb-playwright-runner`)

## Hogyan haladjunk tehát gyorsabban?

* dolgozzon úgy, mint én
  * nem kell magyarázni
  * tudom vállalni érte a felelősséget
* dolgozzon úgy, mint én soha
  * gyorsan
  * párhuzamosan
  * fáradhatatlanul

## Akkor tehát most teljesen kiadjuk magunkat?

* most az nyer, aki gyorsabban és olcsóbban szállít
* a fejlesztők eddig is *collective code ownership*-ben gondolkoztak, aki *kopf-monopol*-ban, annak eddig sem volt jövője



# El kell mondani

* Cél: dark factory
  * Út: *in-the-loop* >> *near-the-loop* >> *out-of-the-loop*
  * Út: *lépésről lépésre*
* Cél: én üzemeltetem
  * Út: erőforrások legalább a fele az *agentic layer*-re megy
* Cél: mindent értek
  * Út: *magyarázd*
  * Út: *úgy csináld, ahogy én tenném*
* Cél: szállító független
  * Út: kis feladatok
  * Út: több agent támogatása
  * Út: *független futtatás*
# Demo terv

## Keretek

- 60 perc, Slidev. A kód a `adw-tutorial` repo, lépésenként egy branch, minden branch
  az előzőre épül. A slide a két branch közti diffet mutatja (rövid, 10-25 soros részletek).
- Minden LLM-futás előre lejátszva: a `.adw/` nyom a branch része (nincs gitignore-ban).
  Élő futás helyett egy `ReplayAgent` adja vissza a rögzített kimenetet, így a demo
  determinisztikus és másodpercek alatt lefut. Élő `claude` hívás opcionális, ha van idő és net.
- Egy lépés = egy koncepció = egy branch = egy "mit változtattunk, mit látunk" slide-pár.
- Elv végig: **az ügynök alkot, a TypeScript dönt** (toolkit P1).

## Időterv

| Perc  | Blokk                                              |
| ----- | -------------------------------------------------- |
| 0-8   | Bevezető (a fenti három szakasz)                   |
| 8-11  | A feladat és a 8 lépés egy ábrán (gráf + ciklus)   |

Vészkijárat: ha a 20. percnél a 4. lépésnél nem tartunk, a 2. és 3. lépés slide-ját
összevonjuk (a branch-ek maradnak), a 8. lépést csak egy slide és a `hook --once` kimenete.

## A példa: ügyfélszolgálati válaszlevél

Fiktív webáruház (`Napsugár Kertészet`, kerti növények és eszközök). Nem kell magyarázni:
jön egy e-mail, válasz megy rá, van, amit az ügyfélszolgálat elintéz, van, amit tovább
kell adni.

```
adw-tutorial/
├── adw.ts              CLI belépés: bun adw.ts <ticket> [--resume|--status|--approve|--reject "..."]
├── engine/             a minimális engine (lépésről lépésre nő)
├── services/           Mailbox, Checker, Jev, Sender: csak itt van külvilág
├── workflow/           a válaszlevél-workflow node-jai és gráfja
├── prompts/            writer.md, fixer.md ({{változók}}, frontmatter allowed-tools)
├── kb/                 tudásbázis, csak ezt olvashatja az ügynök
│   ├── faq.md          nyitvatartás, szállítás, fizetés
│   ├── szabalyzat.md   visszaküldés 14 nap, garancia, reklamáció menete
│   └── hangnem.md      megszólítás, aláírás, tiltott ígéretek
├── inbox/              beérkező levelek, egy JSON fájl = egy ticket (T-1001.json ...)
├── outbox/             jóváhagyásra váró válaszok (7. lépéstől)
├── sent/               elküldött válaszok (7. lépéstől, a "küldés" egy fájlmozgatás)
└── .adw/<ticket>/<execution>/   state.json, log.jsonl, io/, reports/, logs/
```

Minta levelek (a demo mind a hatot használja, lépésenként egyet-kettőt):

| Ticket | Tartalom                                              | Mire jó                                   |
| ------ | ----------------------------------------------------- | ----------------------------------------- |
| T-1001 | "Mikor vannak nyitva szombaton?"                      | triage kódból: sablonválasz, ügynök kimarad |
| T-1002 | "Elszáradt a 3 hete vett leander, mit tehetek?"       | normál L1 ügy, a writer válaszol a kb-ból  |
| T-1003 | "HARMADSZOR írok, a rendelésem nem jött meg!!!"       | dühös hangnem, sürgős, Jev prior a writernek |
| T-1004 | "A webshopban a kosár gomb nem csinál semmit Safarin" | L3, nincs válasz, eszkaláció összefoglalóval |
| T-1005 | "Visszaküldeném, de 20 napja vettem, megy?"           | szabályzat-határeset, L2, emberi döntés   |
| T-1006 | "Szeretnék 200 tuját rendelni céges számlára"         | fontos, nem sürgős, határidővel, jóváhagyás |

A levél letöltése determinisztikus kód (`Mailbox.fetch`, az `inbox/` mappából olvas, az
IMAP-ot szimulálja). Az ügynök csak a `kb/` mappát és a saját input fájlját olvashatja.

## A válaszlevél-ellenőrzés szabályai (`Checker`, 3. lépés)

Kódban, determinisztikusan, mindegyik egy sor a `problems[]`-ben:

1. A tárgy tartalmazza a ticket azonosítót.
2. Megszólítás és aláírás a `hangnem.md` szerint.
3. Tiltott ígéret nincs: "garantál", "biztosan", "ingyen", "azonnal", "mindenképp".
4. Legfeljebb 150 szó.
5. Magyar nyelv (egyszerű heurisztika: ékezetes betűk aránya, néhány kötőszó).
6. Ha a levél rendelésszámot említ, a válasz is tartalmazza.

Ezek egyszerűek, mégis valódiak: megfelelőségi ellenőrzés, amit ma ember csinál.

## Lépések és branch-ek

Minden lépésnél: **Koncepció** (egy mondat a slide-ra), **Diff** (mi kerül be, hány sor),
**Demo** (parancs és amit mutatunk), **Mondat a TAC-hoz** (melyik leverage pontot
igazolja).

### 01-workflow: gráf és ciklus

- Koncepció: a workflow node-ok gráfja és egy ciklus. A node `Outcome`-ot ad vissza, a
  ciklus írja a `state.next`-et, menti a `state.json`-t, és lép tovább a záró node-ig.
- Diff (új fájlok, kb. 80 sor):
  - `engine/Outcome.ts`: `{kind:"next",to} | {kind:"stuck",reason} | {kind:"max_reached",reason}`
  - `engine/Node.ts`: `id`, `step(state): Promise<Outcome>`
  - `engine/Workflow.ts`: a ciklus (olvas, léptet, alkalmaz, ment, naplóz), gráf-validálás
    a konstruktorban (minden él célpontja létezik, van end node)
  - `engine/ScriptNode.ts`, `engine/EndNode.ts`
  - `workflow/graph.ts`: `fetch` (ScriptNode, beolvassa az `inbox/T-1002.json`-t a state-be),
    `draft` (ScriptNode, sablon szöveg: "Köszönjük levelét..."), `end`
  - `adw.ts`: `bun adw.ts T-1002` és `--resume`
- Demo: futtatás, `cat .adw/T-1002/<exec>/state.json`. Megszakítás `fetch` után és `--resume`:
  a folytatás a `draft`-nál indul, mert a state fájl az igazság, nem a folyamat memóriája.
- Slide: a ciklus 15 sora (`while (true) { node = nodes[state.next]; outcome = await node.step(state); ... }`).
- TAC: Architecture ("no surprise"), Presence (kill és resume = nem kell mellette ülni).

### 02-typed-io: nyílt, típusos kommunikáció

- Koncepció: minden node fájlból olvas JSON inputot és Zod sémával validált JSON outputot
  ad. Nincs rejtett állapot, minden lépés visszanézhető.
- Diff (kb. 60 sor):
  - `engine/state.ts`: `EngineStateSchema` (ticket_id, execution_id, status, next, iteration,
    seq, nodes), a workflow `.extend()`-del bővíti (`mail`, `draft`)
  - `engine/NodeOutput.ts`: `NodeOutputBaseSchema` = `status: ok|issues|stuck`, `done[]`,
    `problems[]` (`[severity] hely: összefoglaló`), `stuck_reason?`
  - `engine/NodeFiles.ts`: `io/<seq>-<name>-input.json`, `-output.json`,
    `reports/<seq>-<name>.md` (a riport az outputból generálódik)
  - `Node.track()`: `nodes[name]=running`, mentés, `node_start`/`node_end` napló, `seq++`
- Demo: ugyanaz a futás, most `ls .adw/T-1002/<exec>/io reports`, egy input és egy output
  fájl, egy generált riport.
- Slide: a `NodeOutputBaseSchema` és egy output JSON egymás mellett.
- TAC: Types (a típus hordozza az információáramlást), stdout (a riport a futás tanulsága).

### 03-exec-node: determinisztikus node-ok és a services réteg

- Koncepció: a nehéz, de determinisztikus munka (letöltés, ellenőrzés) ExecNode, a
  külvilág a `services/` mögött. A `DecisionNode` kódban ágazik el.
- Diff (kb. 120 sor):
  - `engine/ExecNode.ts`: `run(state, report, files): Failure | null`, output és riport a `step`-ből
  - `engine/DecisionNode.ts`: `branches: {label, when(state), to}[]`, az első igaz nyer,
    egy sem igaz = `stuck`
  - `services/Mailbox.ts`: `fetch(ticket)` az `inbox/`-ból, `services/Checker.ts`: a 6 szabály
  - `workflow/nodes/Fetcher.ts` (ExecNode a `fetch` helyén), `workflow/nodes/Checker.ts`
    (ExecNode: `check`), `after_check` DecisionNode: zöld → `end`, piros → `end` `issues` státusszal
- Demo: a sablon draft piros (nincs benne ticket azonosító, nincs aláírás), a riport
  `## Problémák` listája mutatja, mi hiányzik. Még mindig nincs LLM, mégis "működik".
- Slide: a `Checker` 6 szabálya 12 sorban és a DecisionNode két ága.
- TAC: Tests (a gate maga a visszacsatolás), Architecture (külvilág egy helyen).

### 04-agent-node: az ügynök belép

- Koncepció: egy ügynök-futás egy headless CLI folyamat, friss kontextussal. Prompt fájl
  `{{változókkal}}`, JSON séma kényszeríti a válasz alakját, egy újrapróbálás a hibával,
  második hiba = stuck. Az ügynök ott kap szerepet, ahol ítélet kell: a levél megírásánál.
- Diff (kb. 150 sor):
  - `engine/agent/Agent.ts`: interface `run(request): AgentResult`
  - `engine/agent/ClaudeAgent.ts`: `claude -p --output-format json --json-schema ...
    --allowedTools Read,Glob,Grep --disallowedTools WebFetch,WebSearch,Bash`, a
    `TYPESAFE_API_KEY` és minden kulcs kiszűrve a gyerekfolyamatból, timeout SIGKILL
  - `engine/agent/ReplayAgent.ts`: a rögzített `io/<seq>-<name>-output.json`-t adja vissza
    (`ADW_AGENT=replay`), a demo ezzel fut
  - `engine/AgentNode.ts`: template metódus `guard`, `input`, `vars`, `apply`; `Prompt.render`
    (`{{ticket_id}}`, `{{input_file}}`, `{{kb_dir}}`), hiányzó változó = hiba futás előtt
  - `prompts/writer.md`: frontmatter `allowed-tools`, a feladat, a kb/ olvasása, a válasz sémája
  - `workflow/nodes/Writer.ts`: output séma = base + `reply: {subject, body}`
  - a `draft` ScriptNode helyére a `Writer` AgentNode
- Demo: `ADW_AGENT=replay bun adw.ts T-1002`: a writer válasza zöld a checkeren. Megmutatjuk az
  `io/2-writer-input.json`-t (ez az egyetlen, amit az ügynök a feladatról tud), a renderelt
  promptot, és a `logs/2-writer.jsonl` transcript egy részletét (milyen fájlokat olvasott).
  Ha van idő és net: `ADW_AGENT=claude` élőben, ugyanez.
- Slide: a `writer.md` prompt (20 sor) és az `AgentNode.step` vázlata (guard → input →
  render → run → validate → apply).
- TAC: Context (friss, csak az input fájl), Prompts (fájl, template, nem chat), Tools
  (allowlist), Documentation (a kb/ az ügynök dokumentációja), Templates (új ügynök minden
  híváshoz).

### 05-loop-limits: ciklus és korlát

- Koncepció: piros gate után az ügynök javít, de a számláló és a határ a TypeScript-ben él.
  `max_reached` és `stuck` a deklarált failure node-ra megy, az sosem pörög.
- Diff (kb. 70 sor):
  - `workflow/graph.ts`: `after_check` piros ága → `fix` (`Fixer` AgentNode, inputja a draft és a
    `problems[]`), `fix` → `check`; `LIMITS = { maxFix: 2 }`; `guard()` a Fixerben:
    `iteration >= maxFix` → `max_reached`
  - `workflow/nodes/Escalate.ts`: failure node, riportot ír "emberi kézbe" státusszal
  - `Workflow.run`: `stuck`/`max_reached` → `failureNode`, a failure node hibája → `end`
  - `prompts/fixer.md`
- Demo: T-1003 (dühös ügyfél): a writer első válasza "azonnal" és "garantáljuk" szavakkal piros,
  a fixer 1. iterációja zöld. A `log.jsonl`-ben látszik: `iteration: 0 → 1`. Második futás
  `LIMITS.maxFix=0`-val: `max_reached`, `escalate` riport. Mindkettő replay.
- Slide: a gráf ábrája a ciklussal, és a `guard()` 5 sora.
- TAC: Attempts (az iteráció a state-ben mérhető szám), Tests (zárt hurok), Plans.

### 06-triage: kód, Jev, olcsó LLM

- Koncepció: a drága ügynök elé olcsóbb szűrők, sorban. Kód: sablonkérdés. Jev: típusos,
  kalibrált ítéletek párhuzamosan. Olcsó LLM: ami szöveget igényel, de nem ítéletet.
  Az ügynök a maradékot kapja, a triage eredményét priorként.
- Diff (kb. 140 sor):
  - `services/Jev.ts`: `judge(name, state, questions)`, `TYPESAFE_API_KEY` nélkül `null`,
    hiba esetén `null` és egy `jev_error` naplósor, sosem stuck
  - `workflow/nodes/Triager.ts` (ExecNode, a `fetch` után):
    1. kód: tárgy/törzs regex a `kb/faq.md` sablonkérdéseire (nyitvatartás, szállítási idő)
       → `template_reply`, a writer kimarad
    2. Jev, egy kérésben, párhuzamos kérdések:
       - `importance`: score 0-1
       - `urgency`: score 0-1
       - `deadline`: choice `none | today | this_week | date_in_mail`
       - `tone`: choice `angry | neutral | friendly`
       - `complexity`: score 0-1
       - `support_level`: choice `L1 | L2 | L3` (L1 ügyfélszolgálat, L2 BA/tesztelő, L3 üzemeltető/fejlesztő)
    3. olcsó LLM (`claude --model haiku`, Read nélkül): 3 soros összefoglaló az eszkalációs
       jegyhez, csak ha `support_level != L1`
  - `after_triage` DecisionNode: `template_reply` → `check`; `L2|L3` → `escalate` (összefoglalóval);
    különben → `write` (a Writer inputjában `triage: {tone, urgency, ...}`)
  - `JEV_THRESHOLDS` a `graph.ts`-ben (pl. `angry` csak `confidence >= 0.7` felett számít)
- Demo: három ticket egymás után, replay: T-1001 (sablon, 0 ügynökhívás), T-1004 (L3,
  eszkaláció, haiku összefoglaló), T-1003 (angry, a writer promptjában látszik a prior).
  A `log.jsonl` `jev` sora mutatja a hat választ és a konfidenciákat.
- Slide: a hat Jev kérdés 12 sorban, és a DecisionNode három ága.
- TAC: Models (a jó modell a jó helyre: Jev ítél, Haiku összefoglal, Sonnet/Opus ír),
  Types (a Choice/Score típusos válasz, nincs parse), Attempts.

### 07-near-the-loop: kész a javaslat, jóváhagyod?

- Koncepció: a workflow magától indul, kidolgozza a választ, de éles műveletet nem végez.
  Jóváhagyást kér, és a válasz ugyanazon a típusos csatornán jön, mint a node-ok között.
- Diff (kb. 90 sor):
  - `workflow/graph.ts`: zöld gate → `propose` (ExecNode: `outbox/<ticket>.md` kiírás, state
    `status: waiting`), a ciklus kilép
  - `approval` DecisionNode a `--resume` belépési pontján: `state.approval.decision`
    `approved` → `send`; `rejected` → `fix` (az emberi jegyzet `should_fix` inputként,
    `source: human`), iteráció számláló megy tovább
  - `services/Sender.ts`: `send()` = `outbox/` → `sent/` mozgatás (a demo nem levelez)
  - `adw.ts`: `--approve`, `--reject "jegyzet"` (a state-be ír és `--resume`-ot hív), `--status`
- Demo: T-1006 (céges tuja rendelés): a futás `waiting`-ben áll, `cat outbox/T-1006.md`.
  `bun adw.ts T-1006 --reject "kérj szállítási címet és céges adószámot"` → a fixer új
  verziója az outboxban. `--approve` → `sent/T-1006.md`, `status: clean`.
- Slide: az `approval` DecisionNode három ága, és a `--reject` jegyzet mint `should_fix` input.
- TAC: Presence (az ember a végén dönt, nem közben), Streak (hány javaslat ment át első
  jóváhagyásra: a state-ből számolható).

### 08-off-the-loop: a poller és a kódban eldöntött kapu

- Koncepció: nincs jóváhagyási pont az alacsony kockázatú ügyeken. Egy állapotmentes poller
  figyeli az inboxot, indít, és a küldést is maga végzi, ha a kapu kódban zöld. A kockázatos
  ügyek a 7. lépés jóváhagyásánál maradnak.
- Diff (kb. 80 sor):
  - `hook.ts`: tick = `inbox/` új fájljai, soros indítás, `--once` a demóhoz, lock fájl
    (egy futás egy repón)
  - `approval` DecisionNode első ága kódban: `check zöld && support_level == L1 &&
    importance < 0.5 && tone != angry` → `send` jóváhagyás nélkül; különben `propose` (várakozás)
  - `.adw/` alapján: a `waiting` futásokat kihagyja, a `clean` futásokat nem indítja újra
- Demo: `bun hook.ts --once` az egész inboxon (replay): T-1001 és T-1002 automatikusan
  `sent/`-be, T-1003 és T-1006 `outbox/`-ban vár, T-1004 és T-1005 eszkalálva. Egy táblázat a
  végén: ticket, út, ügynökhívások száma, iteráció, emberi beavatkozás.
- Slide: a kapu feltétele 4 sorban, és a záró táblázat.
- TAC: ADWs (a legmagasabb absztrakció), Size (egy egész inbox felügyelet nélkül), Streak,
  Presence (zéró a L1 ügyeken).

## TAC zárás (43-57. perc)

A 4 KPI a `.adw/` nyomból számolható, ezt mutatjuk a 8. lépés táblázatán:

| KPI      | Honnan jön                                                       | Melyik lépés adja  |
| -------- | ---------------------------------------------------------------- | ------------------ |
| Size     | node-ok száma egy futásban, tickets száma egy hook tick-ben       | 1, 8               |
| Attempts | `iteration` a state-ben, retry a `node_end` naplóban             | 4, 5               |
| Streak   | egymás utáni `clean` futások a hook naplójában                    | 7, 8               |
| Presence | `approval` döntések száma / összes futás                          | 7, 8               |

A 12 leverage point a lépésekre vetítve (egy slide, egy táblázat):

| Leverage point | Lépés | Egy mondat                                                   |
| -------------- | ----- | ------------------------------------------------------------ |
| Context        | 4     | friss folyamat, csak az input fájl és a kb/                  |
| Models         | 6     | Jev ítél, Haiku összefoglal, erős modell ír                  |
| Prompts        | 4     | fájl, template, séma; nem chat                               |
| Tools          | 4     | allowlist: Read, Glob, Grep; semmi web, semmi bash           |
| stdout         | 2, 3  | riport és transcript minden node-ról                         |
| Architecture   | 1, 3  | gráf + ciklus, külvilág a services mögött, no surprise       |
| Types          | 2, 6  | Zod séma a node-ok közt, Choice/Score a Jev-ből              |
| Plans          | 1, 5  | a gráf maga a terv, a ciklus a tervezett javítás             |
| Documentation  | 4     | a kb/ az ügynök dokumentációja                               |
| Templates      | 4, 6  | prompt fájlok, sablonválasz kódból                           |
| Tests          | 3, 5  | a Checker a zárt hurok                                       |
| ADWs           | 8     | a poller: trigger, környezet, review kódban                  |

Átvezetés az "El kell mondani" záráshoz: *in-the-loop* (1-5. lépés, én futtatom) >>
*near-the-loop* (7) >> *out-of-the-loop* (8). Szállító függetlenség: az `Agent` interface
(`ClaudeAgent`, `ReplayAgent`, később bármi más).
